# Web Application

[Setup](../../docs/setup.md) · [Generated API](../../docs/generated/api/openapi.json) · [Living documentation](../../docs/architecture/living-documentation.md) · [Validation](../../docs/validation.md)

This React/Vite application provides the application shell, a home page, composed product [modules](#modules), and the Living Documentation Portal. It calls the API only through the generated workspace SDK (`packages/sdk`). TanStack Router owns navigation and shareable state in the URL, TanStack Query owns API state, and React owns temporary form/interaction state. The API remains the authority for authorization and business rules.

## Modules

A web module is the browser side of a product capability. It defines its routes as children of the shared root route, keeps its pages, client calls, styles, and wording in its own `src/<module>/` folder, and exports a navigation link component. [`src/modules.tsx`](src/modules.tsx) is the only composition point: it adds the module's routes to the route tree and its link to the header and home page. Shared shell and portal code never import a module. Module browser journeys belong in `test/e2e/<module>/` and may start their own disposable stack with the shared [end-to-end stack helpers](test/e2e/stack.ts). [Orion's reference implementation](../../docs/project-derivation.md#orions-reference-implementation) is a complete example.

Use the shared [`ErrorNotice`](src/components.tsx) and [`api-client.ts`](src/api-client.ts) for public API failures: pass a module's own stable codes when unwrapping responses and its own wording for them. A failed or lost write is an unknown outcome, never proof that nothing changed.

## Entry and home page

Teluni composes its own `/` route from the [`workspace` web module](src/workspace/routes.tsx) instead of the shell's generic home page. A visitor without a session (or when the session service is unavailable) goes to `/sign-in`; a signed-in person sees the home page with their first companies, a path to create the first company, and the session's two-step verification state. `/sign-in` sends a signed-in person on to `returnTo` or the home page, and presents the product beside the sign-in action. The header shows Home, Companies, the session entry and, in development only, Documentation.

The Living Documentation Portal is a development aid, not part of the product (owner direction, 2026-10-19). [`src/modules.tsx`](src/modules.tsx) mounts its routes and header link only when `import.meta.env.DEV` is true, so the Vite development server serves `/docs` while production builds drop the portal's code and generated pages; [`scripts/check-public-bundle.mjs`](scripts/check-public-bundle.mjs), part of `bundle:check`, fails when portal content reaches `dist/`.

## Identity

The display name comes from `.orion/project.json` at build time: page titles, the shell brand, and the portal show the repository's own name. The [brand mark](src/assets/brand-mark.svg) and its derived [touch icon](src/assets/brand-touch-icon.png) belong to the repository. The Orion foundation uses the Orion mark; project initialization replaces both files with a neutral placeholder for the project to redesign.

The shell, documentation navigation, and browser favicon consume the SVG directly. Only the Apple touch icon uses a derived 180×180 PNG on the approved `#F8FAFC` light background. After editing the SVG, run `pnpm -C apps/web identity:write` to regenerate that raster through the [export script](scripts/generate-touch-icon.mjs), using the Playwright Chromium installation described in [setup](../../docs/setup.md#prepare-a-clean-checkout). Commit both files, then rebuild. Do not edit the PNG independently. Adjacent live text names the decorative mark for accessibility.

Teluni uses the owner-approved [Connected Tiles identity](../../docs/project/branding/README.md): the selected symbol, a locally served Plus Jakarta Sans variable font with its OFL notice, titlecase live brand text, and blue/teal/navy palette. The runtime SVG is canonical, and `identity:write` derives its touch PNG. The branding guide owns the single identity kit and remaining domain/trademark evidence.

## Run the application

Use the canonical [setup guide](../../docs/setup.md) for installation, environment loading, and prerequisites. For an API at `127.0.0.1:3000`, run `pnpm -C apps/web dev`.

Vite forwards the default `/api` browser path to the local API and removes that prefix. `ORION_WEB_API_TARGET` changes only the development-server target. `VITE_ORION_API_BASE_URL` is the sole browser API setting, defaults to `/api`, and must be a same-origin path. A deployed static build needs an equivalent same-origin route/reverse proxy; this guide does not select deployment infrastructure. Server-only URLs and credentials must not enter browser configuration.

Human sign-in uses the server-managed session of the API's `identity` module. The [`identity` web module](src/identity/routes.tsx) provides `/sign-in`, `/account/sessions` and the header's sign-in/sign-out entry. Login is a full navigation to `/api/auth/login`; the browser then holds only the API's `HttpOnly` session cookie, and the session's CSRF token stays in module memory for unsafe requests through the SDK. Sign-out clears all cached query data. `loginHref(returnTo, "strong" | "recent")` starts two-step verification when an operation answers `STRONG_AUTHENTICATION_REQUIRED` or `RECENT_AUTHENTICATION_REQUIRED`; the sessions page offers it directly. The header entry neither queries nor shows the session on `/docs` pages, so the portal still makes no API calls while browsing. Copy is localized through a typed pt-BR/en-US catalog in `src/identity/messages.ts`; no i18n library is selected yet. The API still verifies every business request, and production credentials must never be used in tests.

## Companies and branches

The [`organizations` module](src/organizations/routes.tsx) provides `/companies` and `/companies/$companyId`, composed with identity in `src/modules.tsx`. A signed-in person can page through their companies and create a company with its initial responsible-administrator membership. Company administration offers two-step verification when required by the API. Strongly authenticated administrators can create, rename and archive branches, edit the company's name/default language/time zone, and read its change history; other members see only the branches their current grants allow. Company and branch pages, the selected company view (`view=settings` or `view=history`) and history pages live in route search parameters, so reload and browser history preserve them. Changing views clears the previous collection's cursor. API queries remain in TanStack Query and all product calls use the generated SDK with the session cookie and in-memory CSRF token.

Company creation retains its idempotency key across a retry. Branch renames and company-settings drafts retain the version observed when editing started even if their queries refetch; stale-version recovery reloads current data for review. A lost settings response blocks another save until current data is loaded. Successful settings changes invalidate the company detail, company lists and history. Authorization denials stay visible, including direct settings/history URLs without the required capability. Copy is localized through `src/organizations/messages.ts` using the shared browser-locale selection in `src/locale.ts`. Administrators with the `members.manage` capability also get a `view=members` page listing memberships with presentation names/emails from each person's last verified sign-in. Suspending, reactivating or removing a member asks for confirmation that keeps the version observed when the action was requested; a conflict or lost response requires reloading before another change, and restoring an administrator offers recent two-step re-authentication. The responsible administrator shows no lifecycle actions. Each member lists their effective grants with branches and expiry; an administrator can add a grant (role, whole company or selected active branches, optional expiry, with the administration role offered only to the responsible administrator) and revoke one after confirmation. The responsible administrator can propose transferring responsibility from an active administrator's row; the company page shows the pending transfer only to its two parties, with accept or decline for the successor and cancel for the proposer, and offers recent two-step re-authentication when the API requires it. Members with the `invitations.manage` capability get a `view=invitations` page: administrators invite by email with a role, scope, branches and optional expiry (administration only by the responsible administrator), branch managers invite operators to the branches they manage, and the list shows each invitation's state and email delivery with resend and confirmed revoke. The public `/invitations/accept` route moves the credential from the link fragment into the tab's session storage, asks the person to sign in, previews the invitation for the matching verified address and accepts it on explicit confirmation. The [organizations browser journeys](test/e2e/organizations/companies.spec.ts) use the disposable [local identity stack](../../docs/setup.md#try-sign-in-locally), which can also be used manually to open `/companies`.

The [`devices` module](src/devices/routes.tsx) provides `/companies/$companyId/screens` and `/companies/$companyId/screens/$deviceId` ("Telas"), linked from the company page for members with `devices.view`. The list filters by branch and status in route search parameters and shows each screen's branch, state, erasure and last check-in. Members with `devices.manage` pair a screen by entering the code it shows, which travels only in the request body, with a name, branch and rotation. The screen page shows the reported model and resolution as the device's own statement, the latest offline deadline the screen could hold, and lets managers rename it, change rotation among the reported values, move it to another branch and unlink it after explicit confirmation; an unlinked screen with pending erasure offers a reset record. Changes keep the version observed when the page loaded, and conflicts or lost responses require a reload. The [screens journey](test/e2e/devices/screens.spec.ts) simulates the player over HTTP against the local identity stack.

The [`media` module](src/media/routes.tsx) provides `/companies/$companyId/media` and `/companies/$companyId/media/$assetId` ("Mídia"), linked from the company page for members with `media.view`. The library shows thumbnails with kind, dimensions or duration, scope and state in Library, Archived and (with `media.delete`) Trash views, filtered by kind, scope and name in route search parameters, and refreshes itself while items upload or are prepared. Members with `media.upload` choose files (or drop them) and a scope; each file is created and then streamed with per-file progress through `XMLHttpRequest`, which sends the session cookie and CSRF token. The item page previews the display rendition, explains rejections, and offers rename and tags, archive and restore, move to the trash after explicit confirmation, restore from the trash, discard of unusable uploads and download of the original. Changes keep the observed version; conflicts or lost responses require a reload. The [media journey](test/e2e/media/library.spec.ts) processes generated media with real FFmpeg against the local identity stack.

## Living Documentation Portal

In Teluni the portal is served by the development server only (see [entry and home page](#entry-and-home-page)). The `/docs` hub provides separate API, data dictionary, component, and repository-documentation collections, nested local pages, breadcrumbs, page outlines, and full-text search. Reading and synthetic previews need no token, API process, or database. The API explorer sends only explicit requests to the configured same-origin API, keeps tokens in memory, and asks for acknowledgement before writes. See [portal setup](../../docs/setup.md#living-documentation-portal) to run it.

Shared component examples/descriptions belong in [`components.docs.json`](src/components.docs.json) beside the real exports in `components.tsx`. `pnpm docs:references:write` produces [component Markdown](../../docs/generated/components/web.md) and a lightweight catalog, separately loaded pages, and search shards. All `docs/` Markdown and repository README/instruction files are rendered locally; normal documentation links stay in the portal. Regenerate after authored documentation edits too. API/database/error references come from their respective canonical generators. The portal is a presentation of those facts, not another authoring source.

## Validate changes

Run commands from the repository root. `pnpm -C apps/web typecheck`, `build`, `bundle:check`, `test:unit`, `test:browser`, and `test:e2e` are individual package scripts; use `pnpm validate` for the complete gate. After intentional contract changes, follow the [artifact workflow](../../docs/architecture/backend-execution-and-generated-artifacts.md) to regenerate API, SDK, and portal data in order. `pnpm references:check` and `pnpm docs:references:check` detect drift without repairing tracked output.

Browser component tests use Vitest Browser Mode with Playwright: installed Edge on Windows, bundled Chromium on Linux CI. Playwright end-to-end tests use matching Chromium against the emitted API and the Vite web app; module journeys add fresh Testcontainers PostgreSQL, committed migrations, a restricted runtime role, and synthetic identities. Install missing Chromium with `pnpm -C apps/web exec playwright install chromium`; [setup](../../docs/setup.md#prepare-a-clean-checkout) covers system prerequisites.
