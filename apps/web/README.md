# Web Application

[Setup](../../docs/setup.md) · [Generated API](../../docs/generated/api/openapi.json) · [Living documentation](../../docs/architecture/living-documentation.md) · [Validation](../../docs/validation.md)

This React/Vite application provides the application shell, a home page, composed product [modules](#modules), and the Living Documentation Portal. It calls the API only through the generated workspace SDK (`packages/sdk`). TanStack Router owns navigation and shareable state in the URL, TanStack Query owns API state, and React owns temporary form/interaction state. The API remains the authority for authorization and business rules.

## Modules

A web module is the browser side of a product capability. It defines its routes as children of the shared root route, keeps its pages, client calls, styles, and wording in its own `src/<module>/` folder, and exports a navigation link component. [`src/modules.tsx`](src/modules.tsx) is the only composition point: it adds the module's routes to the route tree and its links to the shell navigation and home page. Shared shell and portal code never import a module. Module browser journeys belong in `test/e2e/<module>/` and may start their own disposable stack with the shared [end-to-end stack helpers](test/e2e/stack.ts). [Orion's reference implementation](../../docs/project-derivation.md#orions-reference-implementation) is a complete example.

Use the shared [`ErrorNotice`](src/components.tsx) and [`api-client.ts`](src/api-client.ts) for public API failures: pass a module's own stable codes when unwrapping responses and its own wording for them. A failed or lost write is an unknown outcome, never proof that nothing changed.

## Entry and home page

Teluni composes its own `/` route from the [`workspace` web module](src/workspace/routes.tsx) instead of the shell's generic home page. A visitor without a session (or when the session service is unavailable) goes to `/sign-in`; a signed-in person sees the home page with their first companies, a path to create the first company, and whether two-step verification is enabled, with a recommendation to enable it. `/sign-in` sends a signed-in person on to `returnTo` or the home page, and presents the product beside the sign-in action. The sidebar shows Home, Companies, the session entry and, in development only, Documentation.

The Living Documentation Portal is a development aid, not part of the product (owner direction, 2026-10-19). [`src/modules.tsx`](src/modules.tsx) uses the foundation's `__ORION_INTERNAL_DOCS__` build boundary: the development server serves `/docs`, while default production builds drop the routes, portal code and generated pages. The Vite isolation plugin rejects accidental internal imports; [`scripts/check-public-bundle.mjs`](scripts/check-public-bundle.mjs), part of `bundle:check`, additionally checks Teluni's distributed product artifact. Explicit protected internal builds follow the foundation policy below and are never pilot/public artifacts.

## Identity

The product shell follows the [Connected Tiles interface plan](../../docs/project/implementation-plan.md#pj-41-interface-alignment): desktop navigation is a sidebar and mobile navigation is a disclosure controlled by Menu, with Escape returning focus to the trigger and route selection closing it. Existing modules still own their links and permission checks. The [`CompanyNavigation`](src/organizations/navigation.tsx) contribution, composed in `src/modules.tsx`, adds the current company's name, a link to switch companies through the existing company list, and links to its available workflows throughout that company's routes. The home page uses the existing company list and account state without adding synthetic counts or activity.

Company context comes exclusively from the matched route's `companyId`; no company ID is persisted or inferred from a query parameter. The navigation shares the existing company-detail query and server-returned effective capabilities with product pages. Role names do not make links available. Pending/error access, including a failed refetch that retains old cached data, hides company links; switching companies uses a separate query key without keeping the previous company's data visible. Company view selection follows the URL while ignoring pagination for the selected view, and changing views clears the cursor. The developer portal makes no session/company requests. [`company-navigation.spec.ts`](test/e2e/company-navigation.spec.ts) qualifies context switching, current-section selection, restricted capabilities, desktop/mobile themes and portal isolation; browser component coverage also checks cached access revocation.

[`tokens.css`](src/tokens.css) owns semantic colors and shared spacing/radius values; [`shell.css`](src/shell.css) owns the product structure. Existing product controls, cards and status notices consume those colors. There is no top header on desktop; narrow screens show a bar with only the menu button. A sun/moon switch (“Tema escuro”) at the foot of the sidebar, inside the menu on narrow screens, chooses light or dark. Until a person uses it, the theme follows live `prefers-color-scheme` changes; a choice stores only `teluni.theme=light|dark` in local storage, synchronizes across tabs and persists across reloads. Invalid stored values fall back to System, and unavailable storage leaves selection usable for the current view. No session, credential or tenant information is stored with appearance. Theme state is scoped to the product shell, so the developer portal retains its existing light presentation without reading the preference. The separate Keycloak pages retain their own branded light theme. On desktop widths the sidebar can be collapsed to its icons; the choice stores only `teluni.sidebar=collapsed`, follows the same tab synchronization and storage fallback as the theme, and never affects the mobile menu. The companies page lifts the content width limit and, on desktop widths, sizes its dataset to the viewport with the grid scrolling inside it.

The product shell maps the foundation's inherited `--ui-*` component hooks to these canonical Teluni tokens. Shared Button, TextField and ErrorNotice therefore follow the product's typography, colors, focus and light/dark appearance. Feature forms and business state remain locally owned; adopting the reference set does not replace the existing workflows.

The first PJ-41 increment qualifies home, company entry/forms, denial and sign-in surfaces in both themes, with browser coverage in [`shell.spec.ts`](test/e2e/shell.spec.ts). Company navigation extends the sidebar through company workflows. The device increment adopts the shared controls in pairing and lifecycle forms, retains native confirmation and domain-owned recovery, and adds detailed theme/responsive coverage in [`device-interface.spec.ts`](test/e2e/device-interface.spec.ts). An unknown pairing response requires an explicit list reload before another submission. Remaining modules' detailed states, visual refinement and provider appearance are tracked by PJ-41; shared token adoption alone does not complete that task.

The display name comes from `.orion/project.json` at build time: page titles, the shell brand, and the portal show the repository's own name. The [brand mark](src/assets/brand-mark.svg) and its derived [touch icon](src/assets/brand-touch-icon.png) belong to the repository. The Orion foundation uses the Orion mark; project initialization replaces both files with a neutral placeholder for the project to redesign.

The shell, documentation navigation, and browser favicon consume the SVG directly. Only the Apple touch icon uses a derived 180×180 PNG on the approved `#F8FAFC` light background. After editing the SVG, run `pnpm -C apps/web identity:write` to regenerate that raster through the [export script](scripts/generate-touch-icon.mjs), using the Playwright Chromium installation described in [setup](../../docs/setup.md#prepare-a-clean-checkout). Commit both files, then rebuild. Do not edit the PNG independently. Adjacent live text names the decorative mark for accessibility.

Teluni uses the owner-approved [Connected Tiles identity](../../docs/project/branding/README.md): the selected symbol, a locally served Plus Jakarta Sans variable font with its OFL notice, titlecase live brand text, and blue/teal/navy palette. The runtime SVG is canonical, and `identity:write` derives its touch PNG. The branding guide owns the single identity kit and remaining domain/trademark evidence.

## Run the application

Use the canonical [setup guide](../../docs/setup.md) for installation, environment loading, and prerequisites. For an API at `127.0.0.1:3000`, run `pnpm -C apps/web dev`.

Vite forwards the default `/api` browser path to the local API and removes that prefix. `ORION_WEB_API_TARGET` changes only the development-server target. `VITE_ORION_API_BASE_URL` is the sole browser API setting, defaults to `/api`, and must be a same-origin path. A deployed static build needs an equivalent same-origin route/reverse proxy; this guide does not select deployment infrastructure. Server-only URLs and credentials must not enter browser configuration.

Human sign-in uses the server-managed session of the API's `identity` module. The [`identity` web module](src/identity/routes.tsx) provides `/sign-in`, `/account/sessions` and the shell's sign-in/sign-out entry. Login is a full navigation to `/api/auth/login`; the browser then holds only the API's `HttpOnly` session cookie, and the session's CSRF token stays in module memory for unsafe requests through the SDK. Sign-out clears all cached query data. `loginHref(returnTo, { reauthenticate: true })` signs in again (the password, plus the code when two-step verification is enabled) when an operation answers `RECENT_AUTHENTICATION_REQUIRED`. Two-step verification is optional for each person: the sessions page shows whether it is on and enables or disables it through `twoStepHref`, and `/welcome/two-step`, where the API sends a new person after their first sign-in, suggests enabling it with a skip option. The navigation entry neither queries nor shows the session on `/docs` pages, so the portal still makes no API calls while browsing. Copy is localized through a typed pt-BR/en-US catalog in `src/identity/messages.ts`; no i18n library is selected yet. The API still verifies every business request, and production credentials must never be used in tests.

## Companies and branches

The [`organizations` module](src/organizations/routes.tsx) provides `/companies` and `/companies/$companyId`, composed with identity in `src/modules.tsx`. A signed-in person can page through their companies and create a company with its initial responsible-administrator membership. The list is a shared `DataSet` with single selection: a row is chosen by clicking it or with the arrow keys and shows it only by color, headers sort on click and offer ascending, descending and a value filter with search and select-all, and columns resize. Sorting and filters apply to the loaded page, persist while switching to the form, and previous/next follow the order shown. The toolbar's Exportar menu saves the rows shown as Excel, CSV (`;` separators) or PDF, built in the browser. The company page lists branches in the same kind of `DataSet` (name, status, time zone; `mode` and `record` in its route search), whose form creates a branch or renames and archives the selected one; administrators can create, rename and archive branches, edit the company's name/default language/time zone, and read its change history; other members see only the branches their current grants allow. Company and branch pages, the selected company view (`view=settings` or `view=history`) and history pages live in route search parameters, so reload and browser history preserve them. Changing views clears the previous collection's cursor. API queries remain in TanStack Query and all product calls use the generated SDK with the session cookie and in-memory CSRF token.

Company creation retains its idempotency key across a retry. Branch renames and company-settings drafts retain the version observed when editing started even if their queries refetch; stale-version recovery reloads current data for review. A lost settings response blocks another save until current data is loaded. Successful settings changes invalidate the company detail, company lists and history. Authorization denials stay visible, including direct settings/history URLs without the required capability. Copy is localized through `src/organizations/messages.ts` using the shared browser-locale selection in `src/locale.ts`. Administrators with the `members.manage` capability also get a `view=members` page listing memberships with presentation names/emails from each person's last verified sign-in. Suspending, reactivating or removing a member asks for confirmation that keeps the version observed when the action was requested; a conflict or lost response requires reloading before another change, and restoring an administrator offers signing in again when the API requires a recent authentication. The responsible administrator shows no lifecycle actions. Each member lists their effective grants with branches and expiry; an administrator can add a grant (role, whole company or selected active branches, optional expiry, with the administration role offered only to the responsible administrator) and revoke one after confirmation. The responsible administrator can propose transferring responsibility from an active administrator's row; the company page shows the pending transfer only to its two parties, with accept or decline for the successor and cancel for the proposer, and offers signing in again when the API requires a recent authentication. Members with the `invitations.manage` capability get a `view=invitations` page: administrators invite by email with a role, scope, branches and optional expiry (administration only by the responsible administrator), branch managers invite operators to the branches they manage, and the list shows each invitation's state and email delivery with resend and confirmed revoke. The public `/invitations/accept` route moves the credential from the link fragment into the tab's session storage, asks the person to sign in, previews the invitation for the matching verified address and accepts it on explicit confirmation. The [organizations browser journeys](test/e2e/organizations/companies.spec.ts) use the disposable [local identity stack](../../docs/setup.md#try-sign-in-locally), which can also be used manually to open `/companies`.

The [`devices` module](src/devices/routes.tsx) provides `/companies/$companyId/screens` and `/companies/$companyId/screens/$deviceId` ("Telas"), linked from the company sidebar for members with `devices.view`. The list is a `DataSet` (name, branch, status with erasure, last check-in and synchronization) under server-side branch and status filters, edited in the dataset's Filter modal and kept in route search parameters with the dataset's `mode` and `record`; its form opens the screen's summary with a link to the screen page. Adding a record opens pairing: members with `devices.manage` pair a screen by entering the code it shows, which travels only in the request body, with a name, branch and rotation. The screen page shows the reported model and resolution as the device's own statement, the latest offline deadline the screen could hold, and lets managers rename it, change rotation among the reported values, move it to another branch and unlink it after explicit confirmation; an unlinked screen with pending erasure offers a reset record. Changes keep the version observed when the page loaded, and conflicts or lost responses require a reload. The [screens journey](test/e2e/devices/screens.spec.ts) simulates the player over HTTP against the local identity stack.

The [`media` module](src/media/routes.tsx) provides `/companies/$companyId/media` and `/companies/$companyId/media/$assetId` ("Mídia"), linked from the company sidebar for members with `media.view`. The library shows thumbnails with kind, dimensions or duration, scope and state in Library, Archived and (with `media.delete`) Trash views, filtered by kind, scope and name in route search parameters, and refreshes itself while items upload or are prepared. Members with `media.upload` choose files (or drop them) and a scope; each file is created and then streamed with per-file progress through `XMLHttpRequest`, which sends the session cookie and CSRF token. The item page previews the display rendition, explains rejections, and offers rename and tags, archive and restore, move to the trash after explicit confirmation, restore from the trash, discard of unusable uploads and download of the original. Changes keep the observed version; conflicts or lost responses require a reload. The [media journey](test/e2e/media/library.spec.ts) processes generated media with real FFmpeg against the local identity stack.

The [`programming` module](src/programming/routes.tsx) provides `/companies/$companyId/programming` with Playlists, Layouts and Grupos views, `/companies/$companyId/programming/playlists/$playlistId`, `/companies/$companyId/programming/layouts/$layoutId`, `/companies/$companyId/programming/groups/$groupId` and `/companies/$companyId/programming/screens/$deviceId` ("Programação"), linked from the company sidebar for members with `programming.view` and from an active screen's page. Members with `programming.edit` create company or branch playlists, order items picked from ready media that fits the playlist's scope with seconds for images, choose a cut or fade, create groups over the whole company or chosen branches, and edit a group's or screen's schedules and default playlist; a schedule set is checked by the API before saving and each schedule shows its own conflicts. Group and screen pages preview the next seven days as computed by the API, in a branch zone chosen for a group and in the screen's own zone. Members with `programming.assign` choose a screen's group or individual programming; when the destination has no publication they first confirm that the screen shows the neutral screen until it is published, and otherwise the page names the generation the screen will show. Playlists and groups are deleted after explicit confirmation. Changes keep the observed version; conflicts or lost responses require a reload. Screens also gain an optional time zone that overrides their branch's. The Layouts view ([`layouts.tsx`](src/programming/layouts.tsx)) creates layouts in either orientation, imports exported `teluni.layout` files and edits them on a scaled canvas: areas move and resize by dragging, arrow keys or numeric fields; catalog areas bind catalog fields by role with a presentation and text size; pages choose a media item, a view page or a group for each page-controlled area; two audible areas need a confirmed mix. The API's issues are named by area and page, and the fit report lists records that do not fit; layouts export as JSON. Group and screen pages choose the program's layout, confirming before schedules or defaults are dropped, then edit and preview each area's schedules; a catalog area's default is its view. The [programming journey](test/e2e/programming/journey.spec.ts) builds a playlist, schedules a group and assigns a simulated screen against the local identity stack.

Group pages and the programming of a screen with individual programming add a Publicação section ([`publications.tsx`](src/programming/publications.tsx)): the current generation, a review that shows the counts, the screens that follow the program and every problem that blocks publication (catalog problems of a program with a layout name their area), publishing with the reviewed content digest (a draft changed after the review is refused and must be reviewed again), and the published generations with restore after confirmation for members with `publications.publish`. Group pages also show each member screen's connection and publication state. The screen page in Telas shows the screen's synchronization ([`sync.tsx`](src/devices/sync.tsx)), refreshed every five seconds: connection from the last sync (AT-24), the desired generation, what the screen reports showing and preparing, its playback condition and free storage, each labeled as reported by the screen; the screen list shows connection and publication state per screen. The [publication journey](test/e2e/publications/journey.spec.ts) publishes a group in the panel, lets a simulated player synchronize and verify its statement, manifest and media, and sees the screen reported up to date.

The [`catalogs` module](src/catalogs/routes.tsx) provides `/companies/$companyId/catalogs`, `/companies/$companyId/catalogs/$catalogId` with Itens and Campos views, and `/companies/$companyId/catalogs/$catalogId/items/$recordId` ("Catálogos"), linked from the company sidebar for members with `catalogs.view`. Creation offers three starting points (products with a price in reais, a weekly agenda, or empty) that create ordinary fields. The field editor saves the whole ordered list and shows each field's problems, with how many items cause them, beside the field. Items have an editor per field type and an availability toggle. Each price field of an item has its base price, a price per branch for company catalogs and its promotions; amounts are typed and shown in the person's locale with the field's currency and become integer minor units without floating point ([`money.ts`](src/catalogs/money.ts)). The effective-price preview shows the price in effect at a chosen local time. Publicação nas telas lists what each price change did per program (queued, published as a generation, skipped, blocked or failed, with the reason), refreshed while some are queued, and lets members who publish authorize a blocked or failed one again. The [catalog journey](test/e2e/catalogs/journey.spec.ts) builds a product catalog with a branch price and a promotion, reads the effective prices, publishes a layout program and sees a price change published as its next generation.

## Living Documentation Portal

For component selection, ownership, categories, source metadata and styling/theme practices, follow [component architecture](../../docs/architecture/web-components.md). Inspect existing components before implementing equivalent UI. The public shared entry point stays small; feature components keep their own scope and optional local metadata.

The internal engineering `/docs` hub is available in local development and excluded from production builds by default, together with its catalog, pages, search assets, styles and reference downloads. It provides API, data dictionary, component, and repository-documentation collections, nested local pages, breadcrumbs, page outlines, and full-text search. Reading and synthetic previews need no token, API process, or database. The API explorer sends only explicit requests to the configured same-origin API, keeps tokens in memory, and asks for acknowledgement before writes. See [portal setup](../../docs/setup.md#living-documentation-portal) and [explicit internal builds and access requirements](../../docs/architecture/living-documentation.md#build-and-deployment-boundary).

The portal owns its layout and scoped styles; application UI remains independently replaceable in `shell.tsx`, `home.tsx`, and the project-owned `modules.tsx` and brand assets. Product help and public API documentation use separately approved sources and application-owned presentation under [the audience policy](../../docs/architecture/living-documentation.md#documentation-audiences-and-publication). They never inherit the internal catalog automatically.

Shared component examples/descriptions belong in [`components.docs.json`](src/components.docs.json) beside the real exports in `components.tsx`. `pnpm docs:references:write` produces [component Markdown](../../docs/generated/components/web.md) and a lightweight catalog, separately loaded pages, and search shards. All `docs/` Markdown and repository README/instruction files are rendered locally; normal documentation links stay in the portal. Regenerate after authored documentation edits too. API/database/error references come from their respective canonical generators. The portal is a presentation of those facts, not another authoring source.

## Validate changes

Run commands from the repository root. `pnpm -C apps/web typecheck`, `build`, `bundle:check`, `test:unit`, `test:browser`, and `test:e2e` are individual package scripts; use `pnpm validate` for the complete gate. After intentional contract changes, follow the [artifact workflow](../../docs/architecture/backend-execution-and-generated-artifacts.md) to regenerate API, SDK, and portal data in order. `pnpm references:check` and `pnpm docs:references:check` detect drift without repairing tracked output.

Browser component tests use Vitest Browser Mode with Playwright: installed Edge on Windows, bundled Chromium on Linux CI. Playwright end-to-end tests use matching Chromium against the emitted API and the Vite web app; module journeys add fresh Testcontainers PostgreSQL, committed migrations, a restricted runtime role, and synthetic identities. Install missing Chromium with `pnpm -C apps/web exec playwright install chromium`; [setup](../../docs/setup.md#prepare-a-clean-checkout) covers system prerequisites.
