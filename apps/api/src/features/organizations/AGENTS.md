# Organizations Module

This module owns companies (tenants), branches, memberships, standard role and access profile grants, the responsible administrator and organization audit. Read the [tenant data design](../../../../../docs/project/tenant-data-design.md) and the [permission matrix](../../../../../docs/project/identity-and-access.md#permission-model-and-default-matrix) before changing behavior.

- Every tenant-owned table with its own `id` keeps `(company_id, id)` unique and every tenant reference composite; the structural suite in `test/organizations/integration.test.ts` enforces it on the migrated schema. Join tables and one-to-one extensions without an `id` follow D-01's key exception. Never grant runtime `UPDATE` on `company_id` or `UPDATE`/`DELETE` on audit events.
- Resolve access on every request through `OrganizationService.access`; never cache it beyond the 30-second revocation bound, and never take company, branch or role from a request body as authority. Hidden resources answer `RESOURCE_NOT_FOUND`.
- Role capabilities live in `domain.ts`; administrator and branch-manager grants count only in strongly authenticated sessions (P12). Add a capability with the module that needs it, not speculatively.
- Authority-changing writers lock the company row first, then the involved memberships in ID order, and recheck the actor's current membership and grants inside that transaction (tenant data design rule 5). Reuse `lockAuthority` in `prisma-repository.ts` for grant, status and responsibility writes; invitation writes lock the company, then the invitation, then memberships, and rebuild the actor's access inside the transaction. Do not add another lock sequence.
- Access profiles (`profile-repository.ts`) combine only `delegableCapabilities` from `domain.ts`; never make administration, settings, branch or member management delegable. A profile's assurance is per capability (`strongCapabilities`), never per label. Resolve a profile's current capabilities on every request; profile writes follow the same lock order, and each edit audits its added and removed capabilities and affected grants.
- Grants are added and revoked, never edited in place. Granting company administration and proposing or accepting a responsibility transfer require the responsible administrator (or, for acceptance, the proposed successor) with strong authentication no older than five minutes, checked against the database clock inside the transaction.
- Each change writes its audit event in the same transaction, passing to `writeAudit` the branches the event concerns (none for company-level events); branch managers read only events confined to their branches. Member presentation data comes only from identity's `HumanProfilePort` for principals on an authorized page. Other modules import only `public.ts`.
- Invitations (`invitation-*.ts`, composed as the separate `invitations` module) follow the [D-13 design](../../../../../docs/project/invitation-delivery-design.md). Never look up principals by email; only the accepting session's verified email binds an invitation. Credentials are stored only as hashes, travel only in request bodies and never reach logs. Each invitation and its email commit in one transaction through the mail outbox, and acceptance revalidates the inviter's current authority without narrowing the grant.
