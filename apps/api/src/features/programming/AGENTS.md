# Programming Module

This module owns playlists, programming groups, the draft programs of groups and screens, schedule rules, screen assignments and timelines under the [programming design](../../../../../docs/project/programming-design.md) and [ADR-0029](../../../../../docs/adr/0029-propose-temporal-based-schedule-evaluation-with-shared-fixtures.md). Read both before changing behavior.

- `schedule.ts` is pure: it never reads a clock or the process time zone and takes IANA zone names explicitly. Keep conflict validation in local wall-clock minutes and zone resolution (gaps to the transition instant, repeated hours earlier for starts and later for ends, then the handoff clip) in the evaluator. Every behavior change updates the canonical [fixtures](../../../test/programming/schedule-fixtures.json), which the player (PJ-12) also runs; never change an expected result to make a test pass. `zoneOffsets` describes a zone with the same rules for screens, which resolve local times against it ([player design](../../../../../docs/project/player-design.md#trusted-time-and-zone-offsets)); after changing the fixtures or zone handling, regenerate the player conformance file with `pnpm -C apps/api conformance:write`.
- Human operations resolve access through the organizations `CompanyAccessPort` and take its `lockForWrite` before any programming row. Then lock in this order: screen rows (through the devices port's `describe` with a transaction), settings, groups, layouts, programs, the per-company limits lock that `counts` takes before every count-and-insert, playlists. A resource the caller can see only partly, such as a group spanning a branch outside their reach, answers `RESOURCE_NOT_FOUND`; a screen's views show such a group as `null` and such a playlist by its ID only.
- A rule or default may use a playlist only when every branch its program can reach is inside the playlist's scope; new media in a playlist must be selected through the media port's `requireSelectable` and fit the playlist's scope.
- The module registers the `playlist-draft` media reference guard, the branch archive guard for explicit group spans and the devices move hook. They run inside the other module's transaction and must stay read-only, except the move hook, which updates the screen's settings in the move's transaction.
- Layouts follow the [catalog and composition design](../../../../../docs/project/catalog-composition-design.md#layouts). `layouts.ts` is pure and holds the layout rules, the `teluni.layout` document and the conservative text measure that screens' renderer must never exceed; changing the measure or a limit changes what fits on screens, so update the design and its fixtures with it. After the company access, layout writes lock the layout row (`FOR NO KEY UPDATE` for saves, `FOR UPDATE` for deletion) or take the limits lock (creation), then the programs that use the layout, then bound catalogs through the catalogs port's `requireBindable` (`FOR KEY SHARE`), then new media through the media port. A program operation that reads its layout share-locks the layout before the program, so layouts always lock before programs. Saves replace the whole definition, so an area's key is its only identity: the API keeps keys exactly as given and never renames them, and a key left out removes that area. Program outputs are keyed by area keys (`screen` for a program without a layout), so a layout choice or save that drops outputs with schedules or defaults, or the default of an area that becomes a catalog area, answers `LAYOUT_CHANGE_CONFIRMATION_REQUIRED` until confirmed, under the design's [programs with layouts](../../../../../docs/project/catalog-composition-design.md#programs-with-layouts); the panel keeps saved keys read-only. A program's layout must fit its reach like a playlist (`LAYOUT_SCOPE_MISMATCH`), including after span changes, and a layout that programs use cannot be deleted. Publications refuse programs with a layout until protocol 2. The module registers the catalogs usage guard and the `layout-draft` media guard; both must stay read-only.
- Assignments never edit programs. An assignment needs `confirmUnpublished` only when its destination has no publication, which the publications module answers through `onPublicationFacts`.
- Every change writes its `programming_audit_events` row in the same transaction, with the branches it concerns; details hold names, counts, versions and IDs only.
