# Publications Module

This module owns publications (immutable generations of programs), the screen synchronization exchange, manifest and media delivery to screens, signed authorization statements and screens' synchronization reports under the [publication and synchronization design](../../../../../docs/project/publication-sync-design.md) and [ADR-0030](../../../../../docs/adr/0030-propose-pull-based-screen-synchronization-with-signed-authorization-statements.md). Read both before changing behavior.

- A stored manifest is the exact bytes screens receive and statements sign; never rebuild or re-serialize a stored manifest. The manifest and content digest come only from `domain.ts`, whose key order is protocol 1; a format change is a new protocol, served beside the old one for the support window.
- A screen's desired publication is computed from current rows at each request (its programming source through the programming port, then that program's latest publication); never store or fan out desired state, and never trust a reported publication ID beyond resolving it within the screen's company.
- Manifests and media are delivered only for the screen's current desired publication. Statements list the desired publication and, while it is not active, the reported active and recovery ones that are unpruned publications of the same company; an unpublished source lists none.
- Human operations resolve access through the organizations `CompanyAccessPort`, take its `lockForWrite` with the program's branches, then let the programming port share-lock the source, program and playlists and the media port share-lock the media, and only then take the per-company publication lock (`lockCompany`). Do not add another lock order.
- Each publication or restore writes its `publication_audit_events` row in the same transaction. Signing keys, manifests, statements and credentials never reach logs, audit details or error bodies.
- Screen routes take their pre-authentication limits from `registerDeviceRequestLimits` (per presented credential, under a per-address ceiling); never key them by client address alone, because many screens share one.
- The `publication` media guard and the programming port's publication facts run inside other modules' transactions, must stay read-only and query through that transaction, so they keep protecting media and assignments while this module is unmounted.
- The sync answer's `zoneOffsets` come only from the programming port's `zoneOffsets`, the zone rules its evaluator uses, so screens agree with the preview ([player design](../../../../../docs/project/player-design.md#trusted-time-and-zone-offsets)). The player reads `test/publications/conformance.json`; when the manifest, statements or zone rules change, regenerate it with `pnpm -C apps/api conformance:write` in the same change.
