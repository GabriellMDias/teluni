# Publications Module

This module owns publications (immutable generations of programs), the screen synchronization exchange, manifest and media delivery to screens, signed authorization statements and screens' synchronization reports under the [publication and synchronization design](../../../../../docs/project/publication-sync-design.md) and [ADR-0030](../../../../../docs/adr/0030-propose-pull-based-screen-synchronization-with-signed-authorization-statements.md). Read both before changing behavior.

- A stored manifest is the exact bytes screens receive and statements sign; never rebuild or re-serialize a stored manifest. Manifests and content digests come only from `domain.ts`: protocol 1 for programs without a layout, byte for byte, and protocol 2 for programs with one ([catalog and composition design](../../../../../docs/project/catalog-composition-design.md#publication-protocol-2)). A format change is a new protocol, served beside the old one for the support window.
- Protocol 2 content comes only from the programming port's layout snapshot, taken under the program's locks; it carries prices for the branches the program reaches, so a restore never serves a wider reach.
- A screen's desired publication is computed from current rows at each request (its programming source through the programming port, then that program's latest publication); never store or fan out desired state, and never trust a reported publication ID beyond resolving it within the screen's company.
- Manifests and media are delivered only for the screen's current desired publication. Statements list the desired publication and, while it is not active, the reported active and recovery ones that are unpruned publications of the same company; an unpublished source lists none.
- Human operations resolve access through the organizations `CompanyAccessPort`, take its `lockForWrite` with the program's branches, then let the programming port share-lock the source, program and playlists and the media port share-lock the media, and only then take the per-company publication lock (`lockCompany`). The price processor follows the same order with `lockForMembership` for the intent's authority. Do not add another lock order.
- Automatic price publication follows the [catalog and composition design](../../../../../docs/project/catalog-composition-design.md#automatic-price-publication). The price change listener runs in the catalogs module's transaction: it takes the publication lock shared (`lockPublicationsShared`), so every publication sees a change committed before it, and it only reads and queues. A protocol 2 publication records its catalog copies with their price sequences, settles the intents they include and queues changes the copies missed; never publish a catalog's prices outside `#record`. The processor copies the latest generation (`price.base`), never drafts, rechecks the authority's `publications.publish` on the program, and finishes its intent in the same transaction under its lease.
- Each publication, restore or price publication writes its `publication_audit_events` row in the same transaction. Signing keys, manifests, statements and credentials never reach logs, audit details or error bodies.
- Screen routes take their pre-authentication limits from `registerDeviceRequestLimits` (per presented credential, under a per-address ceiling); never key them by client address alone, because many screens share one.
- The `publication` media guard, the programming port's publication facts and the price change listener run inside other modules' transactions, must query through that transaction (the listener writes only intents), so they keep protecting media and assignments and queueing price changes while this module is unmounted.
- The sync answer's `zoneOffsets` come only from the programming port's `zoneOffsets`, the zone rules its evaluator uses, so screens agree with the preview ([player design](../../../../../docs/project/player-design.md#trusted-time-and-zone-offsets)). The player reads `test/publications/conformance.json`; when the manifest, statements or zone rules change, regenerate it with `pnpm -C apps/api conformance:write` in the same change.
